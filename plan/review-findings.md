## Details

### R01 [high] logSubNodeRun fires nodeExecuteAfter without awaiting or catching it; a failed progress save crashes the process

- **Package:** core
- **Location:** `packages/core/src/engine/workflow-execute.ts:597`
- **Scenario:** AI chat models and tools call ctx.logSubNodeRun on every LLM or tool call. The engine runs `void this.services.hooks?.nodeExecuteAfter?.(...)`. The server hook is async and awaits repos.executions.saveState() when settings.saveExecutionProgress is true. If that save rejects, the rejection is unhandled. The server registers no unhandledRejection handler, so Node's default terminates the whole main or worker process and every tenant's in-flight execution and webhook on it. Ways to trigger it: an agent prompt or tool output containing \u0000, which a tenant can produce on purpose (e.g. String.fromCharCode(0) in the prompt expression or a Code tool); or any transient Postgres error during a progress save. The un-awaited saves can also land after the final finish() save and overwrite the stored state with an older snapshot.
- **Evidence:** Proved with a core vitest: root node -> ai_tool sub-node whose response calls ctx.logSubNodeRun, and hooks.nodeExecuteAfter rejecting for the sub-node. engine.run() resolved 'success', and process 'unhandledRejection' captured 'Error: saveState failed: unsupported Unicode escape sequence'. grep found no process.on('unhandledRejection') in packages/server/src.
- **Proposed fix:** Push the promise into a list of pending hook promises on the engine and await them all at the end of executeNode or process(), so they complete in order and failures are handled. At minimum chain `.catch((e) => this.services.logger.warn('nodeExecuteAfter failed', { error: String(e) }))`. Also make the server's nodeExecuteAfter catch saveState errors itself.

### R02 [high] SSRF guard bypassed by an HTTP redirect to a literal IP address (metadata, loopback, private network)

- **Package:** core
- **Location:** `packages/core/src/http/http-client.ts:98`
- **Scenario:** An editor in tenant A adds an HTTP Request node (or a credential test, OAuth token URL, MCP server URL, AI provider base URL; they all use this client) pointing at https://attacker.example/r. That server answers `302 Location: http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or http://127.0.0.1:port/, http://10.x.x.x/, http://[::1]/). `assertUrlAllowed` only checks the first URL. undici then follows the redirect itself (`redirect: 'follow'`, line 260). The SSRF check lives only in the agent's `connect.lookup` hook, and Node's net/tls connect never calls `lookup` for an IP literal. So the second hop goes unchecked, and the response (for example cloud IAM credentials) comes back into the tenant's run data.
- **Evidence:** Reproduced with a throwaway vitest (since deleted). A front server on localhost (allow: ['localhost'] stands in for a public attacker host) answered 302 to http://127.0.0.2:<port>/x. `client.request({url:'http://localhost:<port>/'})` returned `INTERNAL-SECRET`, the body of the internal server. A direct `client.request({url:'http://127.0.0.2:<port>/'})` threw `SsrfBlockedError`. Code: `createGuardedAgent` only installs `connect.lookup` (lines 98-115), and `fetch(url, {redirect: options.followRedirects === false ? 'manual' : 'follow', dispatcher})` (line 255-262) follows redirects without calling assertUrlAllowed again.
- **Proposed fix:** Check every hop at dispatch time, not only in DNS lookup. Either (a) wrap the Agent with an interceptor, `agent.compose((dispatch) => (opts, handler) => { const u = new URL(opts.origin); const h = u.hostname.replace(/^\[|\]$/g,''); if (net.isIP(h) && !isAddressAllowed(h, h, policy)) throw new SsrfBlockedError(h, h); return dispatch(opts, handler); })`, so each redirect dispatch (a new origin) is checked; or (b) always fetch with `redirect: 'manual'` and follow up to N redirects yourself, calling `assertUrlAllowed` (and keeping the guarded agent) on each Location. Also give the agent a custom `connect` function that rejects IP-literal hosts failing `isAddressAllowed`, as defence in depth.

- **Package:** editor
- **Location:** `packages/editor/src/components/credentials/NodeCredentials.tsx:150`

### R04 [high] In-memory stores (Simple Vector Store, Simple Memory) cap entry counts, not bytes, so one tenant can fill a shared worker's heap

- **Package:** nodes-ai
- **Location:** `packages/nodes-ai/src/nodes/vector-stores/vector-stores.nodes.ts:32`
- **Scenario:** The comment in tenant-store.ts says 'size caps keep a single tenant from exhausting a worker's heap', but the caps only count entries. Nothing limits vector dimensions or pageContent length. A tenant editor points an Embeddings OpenAI credential at their own server (the credential baseUrl is tenant-controlled) or uses text-embedding-3-large. They then insert into up to 20 memoryKeys with 20,000 docs each, spread over many executions so no single execution trips a limit. Memory needed: 20 stores × 20,000 docs × 3,072 dims × 8 B ≈ 9.8 GB, or far more with large fake vectors (an HTTP response may be up to 100 MB). Simple Memory has the same problem: 1,000 sessions × 40 messages × 50,000 chars ≈ 2 GB per tenant, and anonymous users can fill it through a public Chat Trigger. The store persists across executions, so per-execution limits do not help. The worker runs out of memory and in-flight executions of every tenant on that worker die.
- **Evidence:** MemoryVectorBackend.add pushes `vector: vectors[i]` with no dimension or size check and only does `if (this.entries.length > this.maxDocuments) this.entries = this.entries.slice(-this.maxDocuments)` (MEMORY_STORE_MAX_DOCUMENTS = 20_000). It is held in `new TenantStore<MemoryVectorBackend>({ maxKeysPerTenant: 20, maxTenants: 1000 })`. Simple Memory: `bufferStore = new TenantStore<AiChatMessage[]>({ maxKeysPerTenant: 1000, maxTenants: 2000 })`, keeping `Math.max(2*k, 40)` messages of up to MAX_STORED_CHARS = 50_000. Measured: adding 1,000 docs with 20,000-dim vectors grew heapUsed by 160 MB, which scales linearly to 3.2 GB per store and 64 GB per tenant.
- **Proposed fix:** Account usage in bytes per tenant, not by count. In MemoryVectorBackend.add, reject vectors over a dimension cap (for example 8,192) and pageContent over a size cap. Track bytes as roughly 8 × dims + 2 × content length per entry and evict or reject past a per-tenant byte budget, for example by adding a `maxBytesPerTenant` option with a size function to TenantStore. Apply the same byte budget to bufferStore.

### R05 [high] Google Sheets Update / Append-or-Update rewrites every column of the matched row, replacing formulas with their values and overwriting concurrent edits

- **Package:** nodes-base
- **Location:** `packages/nodes-base/src/nodes/apps/google/GoogleSheets.node.ts:346`
- **Scenario:** A sheet has columns email, qty, price, and total, where total is the formula =B2*C2. Update Row with item {email:'a@x', qty:5} reads the sheet with valueRenderOption UNFORMATTED_VALUE (line 167), so total arrives as the computed 6. It then writes the whole row A2:D2 = ['a@x',5,3,6]. The formula in total is permanently replaced by the stale constant 6 (should now be 15), and price is re-sent too. Any cell another user edited between the read and the write is reverted. With Cell Format = RAW, untouched date cells (read as FORMATTED_STRING) become plain text.
- **Evidence:** Scratch test against the FakeHttpClient: the batchUpdate body was [{"range":"'S'!A2:D2","values":[["a@x",5,3,6]]}] and the read used valueRenderOption=UNFORMATTED_VALUE. The existing google.test.ts:417-419 also asserts that the untouched 'name' column is rewritten (['bob@x','Bob','paid']). Code: `const values = headers.map((h, c) => h in entry.data ? cell(entry.data[h]) : (row.values[c] ?? null));` and `updates.push({ range: A{row}:{lastCol}{row}, values: [values] })`.
- **Proposed fix:** Write only the provided columns. For each key in entry.data, push a single-cell ValueRange `${quoteSheet(title)}!${columnLetter(c+1)}${row.rowNumber}` with [[cell(value)]], or contiguous runs of provided columns, into the same values:batchUpdate. Alternatively send `null` for every column not in entry.data, since the Sheets API skips null cells, instead of the read-back value.

### R06 [high] Postgres, MySQL and SMTP nodes resolve the host again after the SSRF check (DNS rebinding reaches the platform's own database)

- **Package:** nodes-base
- **Location:** `packages/nodes-base/src/nodes/apps/sql/Postgres.node.ts:32`
- **Scenario:** A tenant editor creates a Postgres (or MySQL/SMTP) credential with host `rebind.attacker.example`, whose DNS has TTL 0. The first answer is a public IP, so `ctx.helpers.assertHostAllowed(host)` passes. Then `new pg.Pool({ host })` (or `mysql.createPool({host})` / `nodemailer.createTransport({host})`) passes the hostname to the driver, which resolves it again at connect time and gets 127.0.0.1 or the internal Postgres/Redis/SMTP address. In the shipped docker-compose the platform DB is `workflow:${POSTGRES_PASSWORD:-workflow}@postgres:5432`. A tenant who guesses or knows the credentials can then run SQL on the multi-tenant database, which holds every tenant's run data, workflows and sessions. nodes-ai/src/shared/connections.ts already fixes this with `resolvePinnedHost`; nodes-base does not.
- **Evidence:** Reproduced with a throwaway vitest (since deleted). `dns.promises.lookup`, which assertHostAllowed uses, returned 93.184.215.14, and the callback `dns.lookup`, which the driver uses, returned 127.0.0.1 for the same name. `postgresPool(ctx)` with a real `HttpClient().assertHostAllowed` then ran `select inet_server_addr(), current_user, count(pg_database)` and returned `{"addr":"127.0.0.1/32","current_user":"postgres","dbs":"9"}`. A direct `assertHostAllowed('127.0.0.1')` was blocked. The same pattern is at MySql.node.ts:32 then `mysql.createPool({ host })` (line 37), and at SendEmail.node.ts:121 then `nodemailer.createTransport({ host })` (line 124).
- **Proposed fix:** Reuse the pinning approach from nodes-ai `resolvePinnedHost` (move it to core as a helper, e.g. `ctx.helpers.resolveAllowedAddress(host)`). Resolve once, check every address, and give the driver the checked IP literal (`host: address`). Keep the original hostname for TLS SNI and certificate checks (`ssl.servername` for pg, `ssl.servername` for mysql2, `tls.servername` for nodemailer). Reject hosts that start with '/' (pg Unix sockets) explicitly.

### R07 [high] Postgres, MySQL and Send Email SSRF check is bypassable by DNS rebinding: the host is resolved for the check and resolved again by the driver

- **Package:** nodes-base
- **Location:** `packages/nodes-base/src/nodes/apps/sql/Postgres.node.ts:32`
- **Scenario:** A tenant editor creates a Postgres credential whose host is a rebinding name that alternately resolves to a public IP and to 127.0.0.1 or 10.x (for example rbndr.us). assertHostAllowed(host) resolves it once, sees the public IP and passes. pg.Pool is then given the hostname and net.connect resolves it again, getting the internal address. The tenant reaches internal databases such as the platform Postgres, other tenants' infrastructure or cloud-internal services, and can probe and port-scan. - **Evidence:** ChatTrigger.node.ts:36-42 `.map((o) => o.trim().replace(/\/+$/, ''))` and `list.includes(origin.replace(/\/+$/, ''))`. webhooks.ts decorate: `.map((s) => s.trim())` ... `else if (allowed.includes(origin)) { headers['access-control-allow-origin'] ??= origin; ... }`.
- **Proposed fix:** Normalize the same way in decorate(), stripping trailing slashes and lower-casing scheme and host on both sides, or move origin matching into one shared helper used by both.
